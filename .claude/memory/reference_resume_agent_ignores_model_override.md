Confirmed 2026-07-02: multiple background agents spawned with an explicit `model` override (e.g. `model: "opus"`, `model: "sonnet"`) hit the SESSION's default model's quota error on resume via `SendMessage({to: agentId, ...})`, even though their original spawn pinned a different model. This happened right after the lead session's own default model changed (Fable exhausted → switched to Sonnet) — the resumed agents picked up the stale/exhausted default rather than their own spawn-time override.

**How to apply:** if a resumed agent immediately errors with a model-quota/limit message that doesn't match the model it was spawned with, don't retry the resume — it will fail identically, even after the session default model has since changed to something with quota (confirmed: an agent kept hitting the exhausted-Fable error on resume well after the session default was switched to Sonnet). The resume path seems bound to whatever model it resolved to at some point, not re-evaluated per-call. Never retry the same resume twice. Instead: capture whatever state is recoverable (its last report, any PRs/branches it already pushed — git state survives independently), then spawn a FRESH agent with the model pinned explicitly again, briefed with a summary of the terminated agent's progress and pointers to its branches/PRs so no work is repeated. Check `gh pr list` for already-pushed work before re-doing anything — background agents push early, so completed sub-work is usually safe even if the agent process itself is unrecoverable.

**ROOT CAUSE FOUND 2026-07-03** (after dozens of manual respawns across a full session): the "session's current default model" a resumed agent falls back to is NOT a hidden session-level variable — it's the literal `model:` field in the agent-definition frontmatter (`.claude/agents/developer.md`, `senior-developer.md`, `architect.md`, `product-owner.md`). An earlier-session user directive ("devs default fable") had set these files' `model:` to `fable`. My per-`Agent`-tool-call `model: "opus"` param DOES override this for the initial spawn (agents ran fine as Opus at first) — but on `SendMessage`-resume, the harness re-resolves the model from the agent-definition file, not the original spawn param, so once Fable exhausted, EVERY resume of EVERY agent type died identically, all session, regardless of what model each one was originally pinned to.

**PERMANENT FIX (not a per-agent workaround):** edit the `model:` field directly in the agent-definition files to match whatever tier currently has quota. This fixes resume for ALL agents system-wide in one edit, rather than respawning fresh one at a time forever. Check `grep -rn "^model:" .claude/agents/` for the full list before assuming you've caught every file (a `product-owner.md` instance was missed on the first pass since no PO agents had been spawned that session, but it shared the same stale default and would have hit the same bug the moment one was).

**INTENDED CROSS-TIER CONTINUATION PATTERN (user goal 2026-07-04):** the aim is to let in-flight agent transcripts continue on a cheaper tier when a tier's budget exhausts — same transcript, full context retained. Plan the exhausting tier's last tokens on the judgment-heavy parts (classification, diagnosis, design rulings) and let the mechanical tail ride the continuation.

**CAVEAT — the frontmatter flip does NOT reliably rescue an ALREADY-SPAWNED agent (observed 2026-07-04):** flipping `.claude/agents/*.md` `model: fable→opus` and then `SendMessage`-resuming a senior-dev that had been spawned with an explicit `model: "fable"` param STILL crashed on the Fable limit ("You've reached your Fable 5 limit") — twice. So an agent spawned with an explicit model param appears bound to that spawn-time model on resume, and the frontmatter flip only affects FUTURE spawns / agents that inherited the default (not per-call-pinned ones). **Do not count on resuming a specific mid-flight agent across the tier boundary.** Instead, at exhaustion: (1) check whether the agent's DELIVERABLE is already pushed (PR/branch) — background agents push early, so a mid-flight agent whose PR is CLEAN and whose fixes are committed is DONE, not stranded, and needs no resume (this was the actual outcome for fable-2853/#2631: both fixes pushed, park cleared, PR green before the crash); (2) only if genuine work remains, spawn a FRESH agent on the new tier briefed with the dead agent's pushed state + any PR/issue-log handoff notes. Verify PR state BEFORE assuming a resume is needed.
