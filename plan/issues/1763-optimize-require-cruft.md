# #1763 — Clean up residual `require()` cruft in `src/optimize.ts`

Follow-up to **#992** (`require()` cruft), in the wake of the **#1757**
async-compile migration. Two concrete residuals remain in `src/optimize.ts`,
both verified on `main` (HEAD `9571023be`).

## Residual 1 — dead synchronous binaryen path

After #1757, the live optimizer path is the **async** one: all three call sites
in `src/compiler.ts` (lines 156 / 805 / 1045) use
`await optimizeBinaryAsync(...)` → `await import("binaryen")`.

That left the **synchronous** `optimizeBinary` (optimize.ts:137) and the
binaryen `createRequire` loader it calls — `optimizeWithBinaryenPackage`
(optimize.ts:240), whose body does
`createRequire(file://…)("binaryen")` — with **no live callers**.

Repo-wide verification (`git grep -nE 'optimizeBinary\b'` excluding
`optimizeBinaryAsync`, across `src/`, `tests/`, `scripts/`, `benchmarks/`,
`playground/`, `website/`):

- `src/` — no caller of sync `optimizeBinary`; everything uses the async
  variant.
- `tests/`, `playground/`, `benchmarks/` — **none**.
- `scripts/runner-bundle.mjs` — contains a self-contained **generated**
  esbuild snapshot of the old sync function (lines ~58089 / ~60788). This is a
  build artifact, not a source caller; deleting the source function does not
  affect it (it carries its own inlined copy and is regenerated by the
  bundler).
- The remaining matches are issue/docs markdown, not callers.

`optimizeWithBinaryenPackage` is called **only** by sync `optimizeBinary`, so
the two die together. `optimizeWithSystemBinary` and `getNodeImportsSync` are
shared with the async path (the legitimate wasm-opt CLI fallback) and **stay**.

**#1757's plan item 5 said to keep the sync `optimizeBinary` "for any
synchronous caller."** There are none. Keeping it kept a dead
`createRequire("binaryen")` branch alive — exactly the bundler hazard #986/#1756
set out to remove.

## Residual 2 — bare `require("node:fs")`

`optimize.ts:499` (inside `optimizeWithSystemBinary`'s temp-dir cleanup
`finally`) is a literal bare `require("node:fs")`:

```js
const fs = require("node:fs");
fs.rmdirSync(tmpDir);
```

This is exactly the pattern GH #986 reported. **#1756 claimed "no bare require
remains" — that was inaccurate**; this one survived. A bundler that can't bind a
lexical `require` (ESM) or that tries to statically resolve it can choke here.

The fix routes it through the **same dynamic node-builtin shim the rest of the
file already uses** — the `n` (`getNodeImportsSync()` result) is already in
scope in this function and already exposes the fs functions, so the cleanup uses
`n.rmdirSync(tmpDir)` directly (extending the captured node-imports bundle with
`rmdirSync`). No new `require` of any kind. This is the legitimate node-builtin
use of the shim, unrelated to the dead binaryen branch removed in Residual 1.

## Scope guard (don't over-delete)

The `createRequire` shim has two distinct uses; only one is dead:

- **binaryen-via-createRequire** (sync path, `optimizeWithBinaryenPackage`) →
  **dead, removed**.
- **node:child_process / node:fs via createRequire** (the wasm-opt **CLI
  fallback** in `optimizeWithSystemBinary` / `getNodeImportsSync`) →
  **legitimate, kept** — bundlers intentionally can't statically follow it.

## Acceptance

- `git grep -nE 'require\(' src/optimize.ts` returns **only** comments and the
  `createRequire` shim — **no bare `require(...)` call**.
- `tsc --noEmit` clean.
- `--optimize` still works via the async path (a tiny program compiled with
  `optimize: 3` shrinks and emits no "binaryen not available" warning).
- Bundler smoke: `npx esbuild src/cli.ts --bundle --platform=node --format=esm
  --outfile=/dev/null` succeeds with no binaryen/`require` error. (esbuild is
  the available proxy; bun/deno are not installed in this container, so their
  `--compile`/`compile` paths are not directly verified here.)
